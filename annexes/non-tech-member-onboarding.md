# How to review the Framework — for WG members who don't use GitHub

You have been invited to review the **National Framework for Civilian Skydiving Dropzone Operations in India**, a foundational document being drafted by the ACI Skydiving Working Group.

You don't need a GitHub account. You don't need to use Git. This guide explains how to read the latest draft and submit feedback in a way that gets your input properly tracked, attributed, and reviewed.

---

## Step 1 — Read the latest draft

The latest version of the Framework is always available at this Google Doc:

**[ACI Skydiving Framework — Latest Draft (Google Doc)](LINK_TO_BE_ADDED)**

This Doc is **read-only**. It is automatically updated whenever the Working Group approves a change. Don't try to edit it directly — your edits won't save, and you'll be confused when they vanish.

You can read it on any device. You can use Google Docs' built-in comment feature freely for discussion and questions.

---

## Step 2 — Submit feedback

When you have a **proposed change** (text you want added, removed, or changed), submit it via:

**[WG Feedback Form (Google Form)](LINK_TO_BE_ADDED)**

The Form takes about **3–5 minutes** per submission. It will ask:

1. Your name and WG role.
2. Which section your feedback is about (e.g., `§2A.4.1` or "Part 3 SOPs").
3. What kind of feedback (correction, addition, deletion, disagreement, question, other).
4. The current text you're flagging (copy-paste, optional but very helpful).
5. Your proposed change or question.
6. Your reasoning — why does this matter? Cite a source if you have one.
7. Whether this changes a "Mandatory" standard (don't worry if you're unsure — pick "I'm not sure").

Submit **one Form per section or change**. If you have feedback on five sections, that's five Form submissions. This makes it easier to track each one separately.

---

## What happens to your submission

```
You submit the Form
        │
        ▼
The Scribe (a designated WG member) sees your submission
        │
        ▼
If it's clear:    The Scribe converts it into a Pull Request on GitHub.
                  The Pull Request says "Submitted on behalf of [Your Name]
                  ([Your Role]) on [Date]."
        │
        ▼
The full WG reviews the Pull Request.
The Chair (Abhishek) reviews and approves before any change is final.
        │
        ▼
You get an email when:
  - The Pull Request is opened (with a link)
  - The Pull Request is reviewed
  - The Pull Request is merged or rejected (with reasoning)
```

If your submission is unclear, the Scribe will email you for clarification before opening the Pull Request. Please respond promptly — within 5 working days is ideal.

---

## When to use the Google Doc comment feature instead of the Form

| Use the Doc's comment feature when... | Use the Form when... |
|---|---|
| You want to discuss a point | You want to propose a specific change |
| You're asking a quick clarifying question | You disagree with text and want it changed |
| You're making a casual observation | You're flagging a factual error |
| You want other WG members to weigh in conversationally | You want your input to become part of the official audit trail |

Both are valuable. The Form input becomes a formal, tracked Pull Request. Comments are useful for discussion but are not the official record.

---

## What gets tracked

Every Form submission is preserved permanently in a Google Sheet — even submissions that don't become Pull Requests. You always have a record that your input was received.

Every Pull Request preserved on GitHub includes attribution to you (unless you specifically ask not to be attributed in the Form).

This audit trail is important. The Framework is going to ACI Council and ultimately to DGCA. When they ask "where did this requirement come from?", we want to be able to answer precisely.

## Frequently asked questions

**Will my input be ignored if I'm not technical?**
No. The Scribe role exists specifically to make sure non-tech input has equal weight. Your Form submission goes through the same review and approval process as a technical member's GitHub Pull Request.

**Can I see what other members have submitted?**
The Sheet is restricted to Scribe and Chair only — for audit integrity. But once a submission becomes a Pull Request, it's visible to all WG members on GitHub. Tech-comfortable members can show you the Pull Request if you want to see how your suggestion is being handled.

**What if I want to change something I already submitted?**
Submit another Form referencing the same section, and mention in the "Anything else?" field that this revises an earlier submission. The Scribe will link them together.

**What if I want to submit feedback anonymously?**
Possible but discouraged — anonymous feedback degrades the audit trail. If you have a sensitive concern, contact the Chair directly first.

**How fast will my submission be reviewed?**
Scribe triage happens within 2 working days. Conversion to a Pull Request typically within 5 working days. Full WG review of the Pull Request, then merge: typically 5–10 working days, longer for contested points.

**I see a Pull Request on GitHub that I disagree with. What do I do?**
Submit a Form referencing the section it's about, with your concerns. The Scribe will route your concern into the Pull Request review or open a discussion Issue.

**What if the Form is down or I can't access it?**
Email the Chair directly. The Chair can intake your feedback manually.
